# Local Development Runbook

This runbook is the canonical onboarding guide for bringing up `qiko-signal` on a new developer machine.

Use this file only for local setup and local troubleshooting.

- For VPS deploy/redeploy/wipe flows, see [deploy/VPS_PROD_RUNBOOK.md](deploy/VPS_PROD_RUNBOOK.md)
- For deployment policy, AWS SSM naming, and env standards, see [deploy/VPS_DEPLOYMENT_RO.md](deploy/VPS_DEPLOYMENT_RO.md)

The local standard is:

- `ENVIRONMENT=development`
- frontend runs on `http://localhost:3000`
- backend runs on `http://localhost:8000`
- root compose env comes from `.env.development`
- backend overlay comes from `backend/.env.development`
- standalone Next.js env comes from `frontend/.env.local`
- backend secrets come from the local `.env.development` file (no Secret Manager locally)
- local development uses the same real JWT/OAuth authentication flows as production

Google APIs (Gemini, GA4 analytics, Places/Maps, Google OAuth) are configured per-feature via their individual keys/paths in `.env.development` (e.g. `GEMINI_API_KEY`, `GA4_SERVICE_ACCOUNT_JSON_PATH`) — only set the ones you need. There is no generic ADC credentials file.

---

## Service Reference

The local Docker stack (`docker-compose.yml`) runs the following services:

| Service | Port | Purpose | Required? |
|---|---|---|---|
| `db` | 5432 | PostgreSQL 18 database | Yes |
| `redis` | 6379 | Redis 8 (queues, cache, rate limiting) | Yes |
| `backend` | 8000 | FastAPI API server (runs migrations on start) | Yes |
| `ai-service` | 8001 | Separate AI provider microservice | Yes |
| `audit-worker` | - | Redis queue consumer for audit jobs | Yes |
| `email-worker` | - | EmailOutbox polling worker | Yes |
| `pdf-worker` | - | PDF report generation worker | Optional |
| `external-webhook-worker` | - | Outbound webhook delivery worker | Optional |
| `monitoring-worker` | - | Project monitoring worker | Optional |
| `visibility-worker` | - | AI visibility index worker | Optional |
| `performance-worker` | - | Performance snapshot sync worker | Optional |
| `cron-sweeper` | - | Scheduled tasks (commitment renewal, retention) | Optional |
| `frontend-dev` | 3000 | Next.js dev server with hot reload | Yes |
| `frontend` | 3000 | Next.js production build (profile: `production`) | No (use `frontend-dev`) |

**Startup order**: `db` + `redis` first, then `backend` + `ai-service`, then workers (they wait for backend health check), then `frontend-dev`.

## 1. Prerequisites

Install these first:

- `git`
- `docker`
- `docker compose`
- `python3`

If you are on Windows, use WSL for the project workspace.

## 2. Clone the Repository

```bash
git clone <your-repo-url>
cd qiko-signal
```

## 3. Secrets

Local development does not use a secret manager. All local secrets live directly in `.env.development`:

- **Local:** `.env.development` (generated by `scripts/dev-setup.sh` / `scripts/setup-development.sh`) with `SSM_ENABLED=false`. The backend reads these values directly via `backend/core/env_bootstrap.py`.
- **Deployed:** AWS SSM Parameter Store under the `/qiko-signal/` prefix (region `eu-central-1`), overlaid at container startup. This is not used locally.

## 4. Bootstrap the Local Environment

Run the interactive setup:

```bash
./scripts/setup-development.sh
```

Or the legacy non-interactive version:

```bash
./scripts/dev-setup.sh
```

The interactive script walks through 3 steps:

1. **Generate passwords & secrets** — creates `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, JWT keys, session secret, encryption key; writes them to `.env.development` and `frontend/.env.local`, and sets `SSM_ENABLED=false`
2. **Build containers** — starts db, redis, backend, workers, and frontend-dev
3. **Health check** — polls backend `/health` with 60s timeout

It creates or refreshes:

- `.env.development`
- `backend/.env.development`
- `frontend/.env.local`

Fill in any real API keys you need (e.g. `GEMINI_API_KEY`, `FIRECRAWL_API_KEY`, `STRIPE_SECRET_KEY_TEST`) directly in `.env.development`. Keep localhost URLs in `.env.development` and `frontend/.env.local`.

## 5. Start the Local Stack

### Step 1: Start infrastructure

```bash
docker compose up -d db redis
```

Wait for health checks to pass (~10s):

```bash
docker compose ps db redis
```

### Step 2: Start backend and all workers

Core services (always needed):

```bash
docker compose up -d backend ai-service audit-worker email-worker
```

Optional workers (start them if you need the features they support):

```bash
docker compose up -d pdf-worker external-webhook-worker monitoring-worker visibility-worker performance-worker cron-sweeper
```

Or start everything at once:

```bash
docker compose up -d backend ai-service audit-worker email-worker pdf-worker external-webhook-worker monitoring-worker visibility-worker performance-worker cron-sweeper
```

### Step 3: Start the dev frontend

```bash
docker compose --profile frontend-dev up -d frontend-dev
```

### Step 4: Verify

```bash
docker compose ps
```

All services should show `Up` or `healthy`. The backend health check takes ~15-30s.

## 6. Run Database Migrations

The backend container already runs Alembic on startup through `backend/scripts/start-backend.sh`, and the app re-checks Alembic head on FastAPI startup when `RUN_MIGRATIONS=1`.

Usually you do not need a manual migration step in local Docker. Use it only if you intentionally disabled runtime migrations or you are debugging an older container:

```bash
docker compose exec backend alembic upgrade head
```

## 7. Verify the Local Environment

Check the runtime env inside the backend container:

```bash
docker compose exec backend env | egrep 'ENVIRONMENT|SSM_ENABLED'
```

Expected values:

- `ENVIRONMENT=development`
- `SSM_ENABLED=false` (local dev uses pure dotenv; the AWS SSM overlay is disabled)

## 8. Open the App

Use:

- Frontend: `http://localhost:3000`
- Backend docs: `http://localhost:8000/docs`
- Backend OpenAPI: `http://localhost:8000/openapi.json`
- System status: `http://localhost:8000/api/v1/system-status`

### Optional: Local PDF Report Preview

If you are iterating on `backend/services/pdf_reports/templates/`, use the dedicated preview environment instead of the full PDF worker flow:

```bash
./report_dev/setup.sh
./report_dev/start.sh
```

Default routes:

- HTML: `http://127.0.0.1:8005/`
- White-label alias: `http://127.0.0.1:8005/white-label`
- Standard alias: `http://127.0.0.1:8005/standard`
- PDF: `http://127.0.0.1:8005/pdf`
- White-label PDF alias: `http://127.0.0.1:8005/pdf/white-label`
- Standard PDF alias: `http://127.0.0.1:8005/pdf/standard`
- Battle HTML: `http://127.0.0.1:8005/battle`
- Battle PDF: `http://127.0.0.1:8005/pdf/battle`
- Health/data source: `http://127.0.0.1:8005/health`

The preview server defaults to the repo-root `latest_canonical_audit.json`. To swap mock data for a different canonical export, run:

```bash
REPORT_DEV_DATA=/absolute/path/to/latest_canonical_audit.json ./report_dev/start.sh
```

### Optional: Local Stripe Webhook Forwarding

To test Stripe webhooks locally:

```bash
./scripts/dev-stripe-listen.sh
```

This requires the Stripe CLI installed and authenticated.

## 9. Tail Logs

All services:

```bash
docker compose logs -f
```

Specific services:

```bash
docker compose logs -f backend ai-service audit-worker email-worker frontend-dev
```

## 10. Stop the Stack

```bash
docker compose down
```

To also remove the local database volume:

```bash
docker compose down -v
```

## 11. Common First-Day Troubleshooting

### Google login redirects to production

Local OAuth must stay on localhost. If login redirects to `https://qiko.ai`, rebuild the local frontend and backend:

```bash
docker compose down
docker compose up -d --build backend frontend-dev
```

### A secret is missing at startup

Local secrets come from `.env.development`. If backend startup fails because a value is missing, add it to `.env.development` (or re-run `./scripts/setup-development.sh`). There is no Secret Manager to consult locally.

### Local URLs are wrong

Localhost URLs must remain in:

- `.env.development`
- `frontend/.env.local`

Keep `APP_BASE_URL`, `FRONTEND_URL`, and `BACKEND_PUBLIC_URL` pointed at localhost in the local env files.

### `/api/v1/settings/api-keys` returns `500` with `column api_keys.key_prefix does not exist`

That means the headless API migration has not been applied to the database currently used by the backend runtime.

What changed:

- the backend now re-checks Alembic head on FastAPI startup when `RUN_MIGRATIONS=1`
- that covers local `uvicorn --reload` restarts, which previously did not rerun the container entrypoint after a new migration file was added to a bind-mounted dev container

If you are still on an older backend container or `RUN_MIGRATIONS=0`, run:

```bash
docker compose exec backend alembic upgrade head
```

Important:

- locally the backend uses the `DATABASE_URL` from `.env.development` (the local `db` service); no remote secret overlay is involved
- verify the fix by retrying `GET /api/v1/settings/api-keys`; it should return `401` when unauthenticated or `200` when authenticated, not `500`

### `frontend-dev` fails to bind `:3000`

`frontend` and `frontend-dev` both expose port 3000. Only start one of them. For local dev, always use `frontend-dev` (hot reload). The `frontend` service is behind the `production` profile and should not start locally.

### Workers fail with `Connection refused` before backend is ready

Workers depend on `backend: condition: service_healthy`. If you see connection errors, wait for the backend health check to pass first. Check with `docker compose ps backend`.

## 12. Common Reset Flow

If your local stack gets into a bad state:

```bash
docker compose down -v
docker system prune -f
rm -f .env.development backend/.env.development frontend/.env.local
./scripts/setup-development.sh
```
